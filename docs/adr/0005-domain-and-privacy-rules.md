# Exact project domains and future-only privacy rules

## Decision

A project owns one canonical DNS hostname and at most 20 explicit aliases. Hosts cannot belong to two projects, even across organisations: database triggers reject overlapping claims atomically. The canonical host remains the existing `domain` field; tracker IDs, routes and event APIs remain compatible. Configuration rejects schemes, ports, paths, credentials, whitespace and wildcards. Case, one trailing dot and international names normalise to lowercase ASCII DNS form. IP literals and single-label hosts are not supported. Page URLs and origins may use HTTP/HTTPS and ports; the rule identifies hosts, not deployments or TLS identities.

Production collection validates the page host for pageviews, goals and pulses even without Origin (including opaque `null`). A present, non-null Origin must independently name an allowed host. CORS enables browser delivery; these public headers and site IDs do not authenticate a sender. Development retains its deliberate host bypass, with the same authenticated dashboard and privacy rules. Explicit canonical/alias referrers are internal; unlisted subdomains are external.

## Upgrade

Apply additive migration 0006 before serving this collector. It adds empty aliases, excluded paths and a paused page-signal flag. No events, visits, settings, goals, users or organisation assignments are rewritten. Existing implicit acceptance of all subdomains ends. After migration, configure required aliases (including www) before switching the collector; staging is allowed only by listing its hostname. Existing historical attribution remains unchanged.

New projects from the API and supported seed/shared insertion helper explicitly set DNT/GPC on; bot exclusion is on. Existing explicit privacy flags stay untouched. SQLite's original `respect_dnt DEFAULT 0` remains for old writers/rolling compatibility: arbitrary hand-written SQL and old binaries retain that legacy default. Supported new insertion paths specify 1; operators writing their own SQL must specify privacy values. This avoids a table rebuild or a trigger that would override an explicit false choice. Public sharing cannot be enabled; its old stored flag is retained but the API exposes false, and reports remain authenticated.

## Path policy and minimisation

Administrators can exclude up to 20 absolute path prefixes, each at most 512 characters. `/account` matches itself and descendants, not `/accounting`; matching is case-sensitive. `/` excludes everything. Prefixes and incoming paths are percent-decoded up to four times, normalised to Unicode NFC, and repeated slashes collapsed. Malformed/residual escapes, backslashes, control/space characters, query/fragment delimiters and unresolved dot segments are rejected (collection dropped). URL parsing resolves normal dot segments before path validation. Encoded separators therefore cannot bypass segment matching. Overlong paths are dropped, never truncated into another path.

Matching requests are dropped before event, visit or page creation, not redacted into a shared pseudo-page. The current URL is checked on every pulse. Stored page and acquisition entry paths are also checked, so an old token or active visit cannot copy a newly excluded historical path into fresh state. A visit whose entry is newly excluded stays suppressed until inactivity/midnight creates another visit; users can revisit from a new visit later. History remains visible until normal retention; deleting it needs separate authorization. Privacy-denied pulses pause only an existing identity-matched page mapping; the next accepted pulse reanchors its cumulative counter without duration, preventing backfill across the gap. Lost denied signals cannot reveal a privacy transition; duration remains an estimate.

Only utm_source and utm_campaign survive as bounded attribution values. No other query, fragment, full URL or referrer path enters event/visit/page state. The tracker strips those before sending and sends only referrer origin; the server independently extracts minimised fields. Sensitive paths still travel to the collector for rule evaluation. Campaign values and unexcluded paths may contain personal data supplied by a site: there is no automatic detection or legal compliance claim. Exclusion rules need site-specific review. No visitor cookies, localStorage, sessionStorage, IndexedDB identity or stored raw IP/user-agent are introduced.
